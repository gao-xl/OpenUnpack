## 三大核心高价值特性全量落地（方案 A、方案 B、方案 C）
- **方案 A：物理磁盘拓扑感知与 HDD 寻道风暴避免调度 (Physical Disk Topology Scheduler & IOCTL Arbitration)**：
  - Win32 磁盘拓扑探针双通道：在 `crates/infrastructure/src/paths.rs` 中，先以 `IOCTL_STORAGE_GET_DEVICE_NUMBER` 探测物理驱动器编号；复杂分区/卷上自动回退调用 `IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS`（`0x00560000`）获取底层 `extents[0].disk_number`，精准识别逻辑盘符对应的真实物理磁盘序号（如 `PhysicalDrive0`）；
  - 机械硬盘 (HDD) 排他串行化调度：在 `MultiDeviceScheduler` 中严格维护各设备端点（`DeviceEndpoint::Physical`、`Volume`、`Fallback`）的负载计数。同一物理 HDD 上最多允许 1 个高 I/O 活动任务，彻底消除磁臂剧烈寻道造成的吞吐断崖；NVMe/SSD 端点则允许多任务高并发；
  - HDD 解压引擎线程动态压制：新增 `resolve_engine_threads_with_topology`，当检测到任务源或目标位于 HDD 时，若配置为自动线程数（0），自动将底层解压引擎工作线程降级压制为最高 2 线程，消除多线程内卷争夺磁盘队列。
- **方案 B：损坏归档就地抢救与部分提取模式 (Damaged Archive Salvage & Partial Extraction)**：
  - Rust 原生 Zip 引擎流式容灾提取 (`extract_zip_with_sink`)：改造 `crates/infrastructure/src/engine/zip_engine.rs`，在遭遇条目读取失败、CRC 校验失败或分卷截断时，如果处于 `salvage_corrupted == true` 模式，不终止整个解压流程，而是将当前文件标记为 `is_corrupted = true`，记录实际已写入字节数并继续提取后续条目；
  - 外部 7-Zip CLI 容灾解压 (`extract_cli`)：遇到非零返回码但包含有效输出时，在抢救模式下提取已落盘的健康文件，并在状态机中识别标记；
  - 状态机闭环与状态报告：任务节点中若含有 `is_corrupted == true` 的条目，节点状态置为 `salvaged`，任务状态赋予 `salvaged`（已抢救），生成 `salvagedWithCrcWarning` 校验标识并在界面/API 明示已抢救文件数与损坏文件数。
- **方案 C：解压内容自动去重与 NTFS 硬链接空间优化 (Hardlink Deduplication Engine)**：
  - 原生 NTFS 硬链接去重模块 (`crates/infrastructure/src/dedup.rs`)：针对同分区解压输出，执行大小预筛选（跳过唯一大小文件避免不必要 I/O）+ SHA-256 哈希分组，对相同内容文件使用 Windows NTFS 硬链接（`CreateHardLinkW` / `std::fs::hard_link`）转换去重；
  - Win32 `GetFileInformationByHandle` 精准识别硬链接关系（卷序列号 + 64位文件索引号 `nFileIndexHigh`/`nFileIndexLow`），避免重复链接；设计严格的原子备份替换机制（临时改名 -> `fs::hard_link` -> 成功删备份 / 失败即刻原子回退），绝对零数据丢失风险；
  - 抽象 `DeduplicationCandidate` 泛型特征与 `FileLinker` 接口，解耦解压 manifest 与工作目录复制清单，生产环境无缝调用 Win32 NTFS 硬链接，测试环境支持纯内存测试；
  - 在 `Settings` 协议中新增 `deduplicate_hardlinks: bool`（默认启用），在 `StagedPublication::finish_copy` 中自动执行去重，保留完整目录树的同时实现物理存储零重复占用；
  - 前端 `apps/desktop-ui/src/types.ts` 同步补齐 `deduplicateHardlinks` 契约定义。
