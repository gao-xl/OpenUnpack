## ARchivePasswordFinder 逆向技术分析（外部参考项目）

**任务**：对 `C:\Program Files (x86)\ARchivePasswordFinder` 做深度技术分析（功能/机制/效率/架构 + 瓶颈与改进建议），
作为 OpenUnpack「解压工坊」的参考与反面教材。

**方法**：ILSpy(ilspycmd 11.1.0) 反编译 233 个 .cs → 输出至 `.workbuddy/apf_analysis/`；自写 Python 做 PE/CLR 头解析、
UTF-16/ASCII 字符串提取、LiteDB 原始 dump。

**关键结论（已验证）**：
- 技术栈：.NET Framework 4.6.2 / WinForms / Telerik UI；PE32 x86；`requireAdministrator` + `uiAccess=true`。
- 全解决方案受 **DNGuard HVM** 保护：119 文件中 94 个方法体为桩（`DNGuard Runtime library not loaded`）。
  `APFRuntime.dll`(x86) / `APFRuntime64.dll`(x64) 经 PE 解析确认 **无 CLR 头 = 纯原生 HVM 运行时**。
- 工程结构由 PDB 泄漏：`J:\Projects\ARchivePasswordFinder\{Common,Data,CipherFile}\obj\Debug\*.pdb`。
- 云后端域名：`www.jieyamimayun.com`（"解压密码云"）；协议 `RequestDTO{Token,Info}` / `ResultDTO{Code,Info,Extend}`。
- 破解方法枚举：DictionaryAttack / MaskAttack / BruteAttack / CloudAttack；密码源抽象 `IPasswordIterator`
  （Initialize/GetNextPassword）配合组合模式（Dictionaries / RegularExpressions / CloudPasswordIterator）。
- 外部强力引擎：hashcat + John the Ripper jumbo + 7z2hashcat（`PathConfig` 暴露路径常量）。
- 解压器策略：`BaseExtractor` + `Priority` —— Xceed=1 < SevenZipSharp=2 < Unrar=5 < Gzip/Rebex=10 < 7z.exe=11。
- 解压内核：7z.dll 为 **7-Zip ZS**（Igor Pavlov + Tino Reichardt）+ brotli/zstd/lz4/lz5/lizard/flzma2 编解码器；UnRAR 官方源。
- 数据层：LiteDB `MyData.db`，集合 `PasswordEntitys` / `FileEntitys`；**密码明文存储**（实测 dump 出大量站点口令）。

**核心瓶颈判定**：
- P0：以"完整解压"做密码验证（每候选=解压成本）；无首块惰性判定；外部进程路径每次 spawn（+10–30ms）；
  无常驻 Worker 池。
- P1：任务级并发（默认 ExtractRuningCount=1）；Timer 轮询调度；PerformanceCounter 逐进程采样；
  本地库明文；`SimpleLog._logEntryQueue` 无界；DNGuard 全量虚拟化导致零可维护性；主进程 32 位。
- P2：HttpHelper 固定启用 SSL3；MD5/CRC32/HMAC-SHA256 三套哈希并存；自研日志/HTTP；配置无版本迁移。

**产出**：`docs/ARchivePasswordFinder-技术分析报告.md`（含 P0/P1/P2 分级、目标架构图、对 OpenUnpack 的借鉴/规避清单）。

**供 OpenUnpack 复用**：IPasswordIterator 组合模式、BaseExtractor 优先级降级、12 态任务状态机、
TaskExtensions(Retry/WithTimeout/Fallback)、PowerUtilities、CN2JPHelper 编码兜底、TrySmallFileFirst。

**供 OpenUnpack 规避**：以完整解压做验证、每候选 spawn 进程、密码明文落库、Timer 轮询、DNGuard 全量保护。

## APF 借鉴 → OpenUnpack 升级思路提案

**任务**：基于 APF 逆向结论，结合 OpenUnpack 现状（architecture.md / architecture-modern.md /
software-spec.md / function-summary.md / implementation-contract.md）产出升级思路。

**核对方法**：对现有文档做关键词覆盖检测（编码/乱码/休眠/语料/物理盘/拓扑/CandidateLease/派生 等），
标注"已有 / 缺口"，避免重复建议。

**识别出的 3 处真实空白**：
1. **归档内文件名编码（GBK / Shift-JIS / Big5）** —— 现有文档零覆盖。APF 的
   `CN2JPHelper.DetectEncode/ChangeCode/FixErrJisPath` 是今天仍正确的设计。建议改用
   `System.Text.Encoding.CodePages` + 双字节合法性评分，不依赖已过时的 MLang COM。
2. **主动抑制休眠** —— 现有文档只有"睡眠恢复后重建监视基线"（事后），无 `PowerSetRequest` 主动申请。
3. **候选来源的扩展点形状** —— `PasswordResolver` 只从保险库取候选，无流水线抽象。

**识别出的 3 处"想到但没落地/没抽象"**：
- `PasswordProbe` 首块验证层（architecture.md §7 有意图，无独立模块）
- `BackendRouter` + `BackendCapabilities`（单一 7z.dll，无能力声明）
- `DeviceTopologyProvider`（§12/§116 写对了原则，无模块与可观测性）

**关键设计决定（现在必须留的字段）**：
`CandidateLease` 需携带 `CandidateOrigin { Original | TrimmedSpaces | CaseVariant | FromFileName | CorpusId }`。
理由：architecture-modern §16 要求"派生口令不能误当原文成功"，且 outbox 有 `passwordRevision` 幂等键；
现在不留，未来加派生来源要重做 outbox 契约。

**合规提醒**：APF 的 `MyData.db` 内嵌语料**来源与版权不明**，与 MIT 分发不兼容，
不可直接搬运；离线语料需自采并纳入第三方材料收集流程。

**产出**：`docs/plans/2026-10-10-apf-inspired-upgrades.md`（7 条思路 + S/A/B 优先级矩阵 + 不建议照搬清单
+ 与现有文档章节的衔接动作表）。

**注**：魔数识别（原计划建议项）已由并行任务在 `crates/core/src/scanner.rs` 落地
（512 字节头嗅探，覆盖 GZ/BZ2/XZ/TAR/CAB/ZST/ZIP/7z/RAR，测试 `test_expanded_magic_bytes_detection`），
