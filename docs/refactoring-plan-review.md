评审方法：方案文字审查 + 回归代码取证。标 🔍 的结论已经工具核实（读 csproj / grep 引用图 / git ls-files）；标 ◇ 的为推理判断，待裁决。

## 一、总体结论

**方案方向与骨架成立，按现状不可直接执行。** 分层设计、依赖矩阵、波次结构、插件策略与既有规范（architecture-modern.md §11 目标目录）一致，五大必答项（分层/划分/通信/扩展/迁移）覆盖完整。但存在 **2 个 P0**：其一，W6 对 `src/OpenUnpack.Core` 的整体删除建议建立在未经验证的"死代码"判断上，实测会直接破坏 Worker 构建；其二，方案的"冻结"前提与项目当天的活跃功能开发（M1–M3、APF 升级提案）直接冲突，无共存策略。另有 5 个 P1、11 个 P2 需在执行前或执行中修正。

**问题统计：P0 × 2 · P1 × 5 · P2 × 11。**

### 2.3 核查中的新发现 🔍

- `BatchRunner` 的**生产接线状态不明**：grep 显示其调用方只有 OpenUnpack.Core 内部与测试工程，Worker 的 `WorkerOperations.cs` 未出现。方案若要裁决其去留，需先确认它是"仅测试存活的参考实现"还是"有隐藏调用路径"。
- 当天并行落地的 M1–M3（probe IPC、批量候选探测、ManifestPath 落盘）已经出现在 `types.rs`（`candidate_passwords`/`probe_status`/`matched_password`/`manifest_path`），W1 协议提取会自然携带，**不构成额外风险**。

## 四、P1 问题（执行前应修正）

| 编号 | 位置 | 问题 | 潜在后果 | 修复方案 |
|---|---|---|---|---|
| **P1-1** | §8.2 防腐层示意、§8.3 风险表 | 内部矛盾："旧 coordinator 只读/转发"与绞杀者增量迁移冲突——未迁移用例必须由旧实现**继续写入执行**，只读会让功能瘫痪 | 执行者按字面理解会让 W3 期间任务无法推进，或反向造成双写 | 措辞改为"**按用例移交唯一权威**：任一时刻每个用例只有一个权威实现；旧 coordinator 对未迁移用例保持完整读写，迁移一个、移交一个、删除一个" |
| **P1-2** | §8.3 影子运行 | 影子运行对有副作用的 coordinator 不可行（文件写入、Worker 进程、发布改名无法"只比对不提交"） | 给出无法兑现的保障，掩盖真实风险 | 将影子运行**限定于纯逻辑**：命名规则、指纹计算、扫描归组、候选排序、缓存路由决策（这些恰好已是独立自由函数/静态方法，可直接双跑比对）；状态机与发布流程改用"故障注入 + 恢复矩阵验收"（沿用 architecture-modern §15.5） |
| **P1-3** | §8.1 W3 | 2311 行上帝对象的拆解缺内部策略：未定抽取顺序与接缝，而这正是绞杀者重构最常见的死因 | W3 变成无边界的大爆炸式重写，风险集中爆发 | 补 W3 分解顺序：① 先抽纯函数（coordinator.rs 底部已存在 30+ 个自由函数：`fingerprint_for_group`/`unique_candidates`/`strip_single_root_wrapper`/`validate_target_tree` 等，零行为风险）→ ② 状态机入 domain → ③ 发布/清理入 infrastructure → ④ 最后拆调度循环。每步独立 PR + 回归。W0 同时补 coordinator 专项覆盖缺口分析（当前测试以集成路径为主，恰是风险最高处覆盖最薄） |
| **P1-4** | §7.1 插件契约 | 插件安全模型不完整：未定义插件对口令的访问策略；能力声明的强制执行点未说明 | L2 外部进程插件可能接触敏感数据，违反项目"口令不外泄"基线 | 明确：插件**永不**获得密码库内容；最多经核心中介以单次候选租约方式调用引擎；能力声明在注册表加载时校验 + 每次操作前复核；插件不得写任务库与发布目录（方案已写后者，补前三条） |
| **P1-5** | 全文 | 无量化重构成功指标，各波次"验收门槛"依赖定性判断 | 波次完成与否可争议，重构可能无限拖延或提前宣布胜利 | 增补指标：依赖违规数=0（CI 守卫）、单文件行数上限（建议 ≤800）、domain 单测覆盖率目标、金丝雀样本行为零差异、构建时间不劣化超 10%、W3 期间 PR 冲突率 |

## 六、经评审确认成立的关键设计（无需改动）

- 分层与依赖方向矩阵（修正 P2-1 后）；
- 核心系统/业务模块的四条判定测试（不变量/替换/变化频率/数据所有权）；
- 三条通信边界与协议单源生成策略；
- 三级插件策略中"L1+L2 首版、L3 留接口"的克制选择（与 architecture-modern"首版不开放第三方加载"一致）；
- 四类版本号独立演进与兼容判定矩阵；
- W0→W6 的波次骨架本身（需按 P0/P1 修订细节，但顺序与可回滚原则正确）。
