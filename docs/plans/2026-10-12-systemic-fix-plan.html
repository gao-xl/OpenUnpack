1. 方案背景与核心目标

在经过多轮代码审计与场景推演后，OpenUnpack 暴露出了明显的“系统工程底座”与“日常桌面软件”两层割裂：

架构与系统层痛点

1. crates/core 与 application/infrastructure 双轨并存，基础设施层反向依赖 Core；
2. Worker 假定短进程，C# 端却按常驻服务设计状态机；
3. 盲目全局并发导致机械盘磁头严重寻道崩盘；
4. 杀软锁盘直接被判为不可逆 IoError。

交互与体验层痛点

1. 添加文件引发“扫描中 → 检查结果 → 批次选项”三层 Modal 轰炸；
2. 添加任务后不自动开始，用户误以为卡死；
3. 密码错误后没有即时密码输入入口，被迫去密码库建档；
4. 任务停止超时后由于保护锁阻断删除，造成界面假死。

修复目标与收益

1. 彻底切流：P5 退役 crates/core，统一到 DDD 干净分层；
2. 物理感知：同物理盘严格串行队列，跨物理盘放开并发；
3. 体验降噪：单文件拖入静默入队，即时密码弹窗一键解密，支持 5 秒超时强杀与强行移除。

2. 底层系统与架构逻辑根治方案

2.1 [P0] 架构双轨切流与反向借用核销（实施 P5）

彻底解决 desktop-host 依然运行单体 Core，而 infrastructure 反向依赖 Core 的架构死结。

  • 迁移核心调度引擎：将 crates/core/src/coordinator.rs 的状态机与调度队列彻底迁移至 crates/application/src/use_cases/coordinator.rs，将内存任务状态持久化接口对接 openunpack_application::TaskStore（底层为 SQLite WAL）。
  • 迁移 IPC 客户端：将 crates/core/src/worker.rs 下沉至 crates/infrastructure/src/worker/client.rs，解除 crates/infrastructure/Cargo.toml 对 crates/core 的依赖项。
  • Host 生产切流：修改 apps/desktop-host/src/lib.rs，直接实例化 openunpack_application::TaskCoordinator，注销对 openunpack_core 的全量引用，随后将 crates/core 从 Cargo 工作区中物理退役。

2.2 [P1] 物理磁盘感知与 I/O 调度器重构

解决 HDD 机械硬盘在 4 并发解压时磁头寻道剧烈衰减（吞吐从 120MB/s 暴跌至 15MB/s）的物理逻辑缺陷。

  • 物理驱动器识别：在 Windows 下通过调用 IOCTL_STORAGE_GET_DEVICE_NUMBER 或根据驱动器根路径获取物理盘 DeviceID（如 \\.\PhysicalDrive0、PhysicalDrive1）及媒体类型（HDD 旋转介质 vs SSD 固态闪存）。
  • 分区隔离队列：
    调度规则：同一个物理 HDD 驱动器上，强制限制并发度上限为 1（串行 FIFO 执行）；仅当源/目标处于不同的物理驱动器或 NVMe SSD 时，才允许按照 Settings.concurrency 启动并发。

2.3 [P1] 杀毒软件排他锁（Sharing Violation）防御循环

在 Windows 系统中，文件落盘关闭流瞬间会被 Windows Defender、360、火绒等实时拦截扫描，造成短时间文件无法读取。

  • 在 Worker 和 Host 中进行文件摘要计算、移动重命名和回读校验时，捕获 Windows ERROR_SHARING_VIOLATION (0x20) 和 ERROR_LOCK_VIOLATION (0x21)。
  • 引入指数退避重试机制：初始等待 50ms，以 1.5 倍步长递增，最大重试 5 次（总窗口约 1.5 秒）。若在重试窗口内锁释放则静默恢复，不再将杀软临时扫描误判为 IoError。

2.4 [P1] 跨平台同名大小写冲突自适应重命名

解决 Linux 归档中 readme.txt 与 README.TXT 在 Windows 下直接被系统判定为 UnsafePath 导致解压全面崩溃的问题。

  • 预检层（SevenZipEngine.cs）检测到路径仅大小写不同时，不抛出异常。
  • 自动触发安全重命名规则：为冲突项追加自增序号后缀（如 README (case-conflict-1).TXT），并在 Manifest 记录映射关系，保证合法 Linux 包在 Windows 上能 100% 完整提取。

2.5 [P1] SSD 两阶段缓存空间 3 倍膨胀熔断保护

  • 在启动启用缓存的任务前，进行两阶段全链路预检：SSD可用空间 >= 预估解压体积 * 1.1 + 保留空闲阈值 且 目标盘可用空间 >= 预估解压体积 * 1.1。
  • 若 SSD 缓存空间不足，但目标盘空间充裕，系统自动静默降级为 Direct 直写模式，并在任务消息中提示：“SSD 缓存空间不足，已自适应回退至目标卷直接解压”，避免挤爆 C 盘。

3. 使用与交互逻辑（UX）全面重塑方案

3.1 消灭三层弹窗轰炸：轻量入队与侧边抽屉

用户场景 原流程（痛点） 重构后新流程（顺畅心智）
拖入 1 个压缩包 等待模态框 → 820px 检查结果弹窗 → 本批次选项弹窗（至少点 3 次） 静默直接入队：右下角弹出轻量 Toast：“已添加 xxx.zip”，默认按照全局设置进入准备状态。
拖入文件夹 / 批量包 强制全屏阻断等待，多层弹窗层叠 主界面顶部展开就绪卡片：以非阻断方式在表格上方展示“已发现 8 个分卷包”，提供【开始解压】与【批次配置抽屉】。
修改本次输出选项 弹窗套弹窗（Modal in Modal） 点击侧边滑出的设置抽屉（Drawer），单屏完成修改并立即生效，不遮挡任务主列表。

3.2 添加任务后“默认自动开始队列”

  • 新增配置项 autoStartQueue: boolean（默认开启 true）。
  • 用户拖入文件或点击添加后，任务进入队列的同时自动驱动调度器开始工作。
  • 仅当用户主动点击过【暂停队列】时，系统才保持暂停，并在顶部提供黄色常驻警示条：“队列已暂停，新任务已排队等待处理 [继续队列]”。

3.3 破除密码死胡同：任务条目直接提供即时解密入口

原严重断点：加密文件解压失败后变为 needsPassword，列表只有“重试”按钮（点重试依然用旧密码库再错一次）。用户无法单点输入密码，被迫跳转到【密码库】页面新建密码条目，再返回重试。
  • 列表直接赋能：状态为 needsPassword 的任务，操作列将【重试】替换为显目的蓝色【输入密码】按钮。
  • 即时弹窗设计：点击弹出极简浮层： 
    [ 输入解压密码: **********               ] (支持显示明文)
[x] 同时将该密码保存至我的永久密码库（可选）
[  立即解密并重试  ]   [ 取消 ]
  • 点击后直接将该密码作为优先凭据注入当前任务并立即重试，彻底消灭“为解密一个临时文件必须先在库里建档”的反人类链路。

3.4 5秒超时强杀机制（消除“拒绝删除”引发的假死）

  • 当任务处于 stopping 或 cleanupPending 状态时，正常等待底层进程和文件句柄释放。
  • 若超过 5 秒底层仍未确认退出，【删除任务】按钮解除禁用，变为红色【强行终止并移除】。
  • 点击后，Host 调动底层 Win32 API TerminateProcess 强杀对应的子进程 JobObject，暴力解绑锁并清理残留注册表项，将控制权 100% 交还给用户。

3.5 批量解压页与处理记录页职能纯化

  • 《批量解压》（活动工作台）：仅展示正在处理、等待中、以及本次会话需要用户处理（如输密码、重试）的任务。
  • 自动流转归档：任务一旦 100% 完成且清理完毕，自动从《批量解压》列表中隐去，流转沉淀至《处理记录》历史表中，无需用户频繁手动点击“清除已完成”。

4. 规划功能（F3 / F5 / F1 / F6 / F4）的协同落地

功能代号 功能名称 核心落地点 协同防御要点
F3 CPU自适应与进程优先级调节 三端契约同步 engineThreads 与 workerPriority；Windows 启动进程时传递 IDLE_PRIORITY_CLASS / BELOW_NORMAL_PRIORITY_CLASS；7z 传递 -mmt 参数。 后台解压不再造成用户前台打字或播放视频卡顿；契约套件强校验字段一致性。
F5 CRC 损坏忽略与抢救性提取 7-Zip 遭遇 CRC 损坏（退出码 2）时，支持抢救完好文件，将任务状态落盘为新三态 salvaged（抢救提取）。 严格熔断源文件删除；清单中标记损坏文件，豁免损坏项的完整校验，向用户清晰展示损坏报告。
F1 ZIP 文件名乱码识别与重命名修复 绕开 7z.dll 的默认 OEM->Unicode 转换，直接二进制解析 ZIP Central Directory 原始名字节，通过 GBK/Shift-JIS/Big5 判定打分。 解压完成后结合安全映射清单进行原子重命名，杜绝原始字节丢失造成的不可逆乱码。
F6-① 解压后空目录清理 任务交付前的后处理阶段（Post-processing），自底向上递归清理空文件夹。 若压缩包原本就包含空目录，在生成 Manifest 和回读校验时需同步标记空目录豁免，防止报“缺失目录”校验失败。
F4 多后端解压引擎扩展 抽象 IArchiveBackend 统一接口，按格式路由（7z / 纯 tar / zstd / 系统原生）。 为 WIM、LZH 等格式放开白名单前，必须经过能力矩阵与样本回归测试。

5. 四阶段实施路线图（Implementation Roadmap）

Phase 1: 交互闭环与快速体验重构 (1-2 天)

1. 任务条目集成【即时输入密码】弹窗与一键重试；
2. 默认开启【添加后自动开始队列】；
3. 单文件拖入静默入队，消灭多层模态弹窗；
4. 增加 5 秒超时强杀与强制移除兜底逻辑。

Phase 2: 核心功能与性能落地 F3 + F5 + F1 (2-3 天)

1. 落地 F3：完成跨语言三端契约同步，支持引擎线程与进程优先级调节；
2. 落地 F5：引入 salvaged 状态机，完成 CRC 容错与抢救模式，锁死源文件清理风险；
3. 落地 F1：编写轻量级 ZIP 中央目录原始字节探测器与安全批量重命名。

Phase 3: 底层韧性与硬件感知 (2 天)

1. 引入物理驱动器识别，实施同物理盘串行、跨物理盘并发调度；
2. 落地杀毒软件排他锁（Sharing Violation）指数退避重试循环；
3. 实施 SSD 两阶段缓存 3 倍空间预检与自动 Direct 降级熔断；
4. 落地 F6-① 空目录清理与校验协同。

Phase 4: 生产架构彻底统一 (P5 实施) (2-3 天)

1. 将 Coordinator 完整重构并迁入 openunpack_application；
2. 将 Worker IPC 客户端迁入 infrastructure，切断反向依赖；
3. 桌面 Host 全量改接 Application，彻底物理退役 crates/core。

6. 质量门禁与验收指标

  • 契约门禁：运行 node scripts/check-contracts.mjs --self-test，确保 Rust / C# / TS 三端 DTO 字段类型、可选性与序列化规则 100% 严格一致。
  • 回归测试：全量通过 cargo test（包括并发管线、资源恢复回归用例）与 apps/desktop-ui 97+ 项 Vitest 测试。
  • 异常注入验证：
    1. 使用带真实密码与错误密码的样本验证即时弹窗解密流，确认无需进入密码库即可一键解开；
    2. 模拟占用（如后台句柄锁定）验证 5 秒强杀兜底，确认任务列表不发生僵死；
    3. 构造真实 CRC 损坏 7z 包，验证 F5 抢救提取成功落盘且源文件不被误删；
    4. 在同一物理 HDD 磁盘同时加入 4 个大任务，验证系统自动串行执行、磁头吞吐平稳不发生抖动。
