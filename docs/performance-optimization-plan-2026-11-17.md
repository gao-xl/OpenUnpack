# 性能优化方案（可落地）

> 生成日期：2026-11-17
> 前置依据：[优化问题清单](optimization-issues-2026-11-17.md)（OPT-001 ~ OPT-008）
> 范围：仅优化；不改变功能语义、不改动归档格式、不迁移现有数据目录。

## 二、方案明细

### SOL-01：前端聚合进度快照引用修复

- **适用问题类型**：渲染正确性、高频事件、无效缓存。
- **预期收益**：修复批量进度卡（数据量、实时速率、预计剩余）不随实时事件刷新的用户可见问题；保留按任务隔离订阅。
- **实施优先级**：P0（先于结构优化）。
- **落地步骤**
  1. 在 `progressStore.ts` 增加 `aggregateRevision`，每次进度事件递增。
  2. `useAggregateProgress()` 的 `getSnapshot` 返回 `{ version, entries }` 或不可变快照，保证引用变化。
  3. 保留 `useJobProgress()` 的按任务订阅不变。
  4. 补组件渲染计数断言。
- **潜在风险**
  - 不可变快照产生额外复制；聚合规模可控，风险低。
  - 若返回对象每次新建，需保证同版本返回同一引用，避免无限重渲染。
- **验证指标**
  - `npm test -- progress-store.test.tsx` 全绿。
  - 新增测试：连续两次进度事件触发两次渲染；最终显示第二次进度。
  - 手动：批量任务运行时观察速度与剩余时间持续变化。

---

### SOL-02：进度监听生命周期重构

- **适用问题类型**：连接模式切换、事件串源、监听器泄漏。
- **预期收益**：消除“原生→daemon→原生”切换后实时进度缺失或旧事件污染；统一监听清理语义。
- **实施优先级**：P0。
- **落地步骤**
  1. `api.onProgress()` 返回真正可执行的取消函数，并记录当前 `connectionEpoch`。
  2. `progressStore` 改为按连接生命周期初始化/销毁监听，而非模块级一次性初始化。
  3. 连接切换时取消旧监听、建立新监听。
  4. 补“原生 → daemon → 原生”回归测试。
- **潜在风险**
  - 生命周期改错会漏掉事件或重复注册；用 epoch 校验和幂等清理规避。
- **验证指标**
  - 新测试断言：daemon 模式下原生事件不投递；切回原生后重新收到事件。
  - 手动：两种模式下切换连接，确认进度条持续更新且无串任务。

---

### SOL-03：快照分域缓存与增量投影

- **适用问题类型**：后端全量构建、CPU、内存分配、锁竞争。
- **预期收益**：历史/密码/嵌套节点较多时，快照构建从“每次全量克隆 + 比较”降为“仅变化项”。
- **实施优先级**：P1（结构收益最大，风险中等）。
- **落地步骤**
  1. 先做无行为变化的第一层：密码库 revision 未变时复用上次投影，避免每次重建全部 `PasswordView`。
  2. 任务侧在 `view_state` 下维护不可变投影，`put` 只替换对应任务。
  3. “最近 20 条历史”维护增量索引，替代全量筛选排序。
  4. 保留 delta 协议与基线一致性，扩展测量用例覆盖 1000/10000 记录。
- **潜在风险**
  - revision、session、基线一致性若出错会造成状态错乱；必须用既有 snapshot_projector 测试 + 并发测试约束。
  - 复用缓存需要处理 `vault` 失败/恢复分支。
- **验证指标**
  - `./scripts/measure-load.ps1 -Worker <冻结Worker> -Profile snapshots`。
  - 记录快照构建 p50/p95/p99、序列化字节数、峰值内存；对比 10/1000/10000 三档。
  - 现有 `snapshot_projector` 单元测试全绿。

---

### SOL-04：watcher 去 O(n²) 与目录复用

- **适用问题类型**：后台 CPU、磁盘 I/O、电量、长期内存增长。
- **预期收益**：降低监听线程在高分卷/大目录场景的开销。
- **实施优先级**：P1（低风险、易落地）。
- **落地步骤**
  1. `to_remove` 改 `HashSet<PathBuf>`，消除 `contains` 线性扫描。
  2. 按“父目录 + 分卷 stem”分组，每个 tick 每个目录最多 `read_dir` 一次，复用结果。
  3. preflight 持续失败候选采用指数退避。
  4. `enqueued_history` 增加容量/TTL 或紧凑指纹轮换。
- **潜在风险**
  - TTL 可能让“同路径、同大小、同 mtime 替换”重新入队；用容量上限 + 明确注释规避。
  - 退避过激会延迟真实完成的下载被发现；需要可调参数。
- **验证指标**
  - 新增确定性测试：多分卷、大目录、持续 preflight 失败。
  - 负载测量记录 watcher 线程 CPU、目录读取次数、常驻内存。

---

### SOL-05：最近历史增量索引

- **适用问题类型**：排序、CPU、临时分配。
- **预期收益**：每次快照/历史分页不再全量排序，只取最近 N。
- **实施优先级**：P2（随规模提升）。
- **落地步骤**
  1. 队列快照用固定容量堆或 partial select 取最近 20。
  2. 历史页维护按 `created_at,id` 排序的增量索引，或逐步下推 SQL 排序分页。
- **潜在风险**
  - 增量索引需覆盖新增、删除、重试、恢复四条路径，缺一不可。
- **验证指标**
  - 10000 历史记录下比较排序耗时 p95 与临时分配。
  - 历史分页返回结果与现实现一致。

---

### SOL-06：SQLite `publications(job_id,state)` 索引

- **适用问题类型**：数据库查询、长期数据增长。
- **预期收益**：删除任务、恢复检查、清理历史成本更稳定。
- **实施优先级**：P2。
- **落地步骤**
  1. 新增 `user_version` 迁移，创建 `idx_publications_job_state`。
  2. 增加旧库升级 + 失败回滚测试。
- **潜在风险**
  - 迁移失败必须回滚，不能半升级；写入路径有轻微开销。
- **验证指标**
  - 迁移测试：旧库升级后索引存在；注入故障时整体回滚。
  - `EXPLAIN QUERY PLAN` 显示按 `job_id,state` 命中索引。

---

### SOL-07：扫描去重复读取

- **适用问题类型**：磁盘 I/O、扫描耗时。
- **预期收益**：减少大目录扫描的文件打开与 SFX 重复读取。
- **实施优先级**：P2。
- **落地步骤**
  1. 单次读取后缓存 SFX 判定，消除 512KB 重复读取。
  2. 常见扩展先走快速路径。
  3. 为 10 万混合文件目录建立扫描基准。
- **潜在风险**
  - 若跳过魔数识别会改变伪装归档发现能力；先只去重复读取，行为改动单独评审。
- **验证指标**
  - 普通/伪装/显式 SFX/伪 SFX 四组回归全绿。
  - 10 万文件扫描耗时与读取字节数对比。

---

### SOL-08：超大模块拆分

- **适用问题类型**：可维护性、可读性、并行协作。
- **预期收益**：降低冲突概率与审查成本。
- **实施优先级**：P2（长期）。
- **落地步骤**
  1. 优先拆纯逻辑：`QueuePage` 拆扫描选择、密码提交、批量统计、操作列、删除流程。
  2. `commands.rs` 按历史、队列控制、重试、删除分模块。
  3. 每次拆分保持公开行为不变，并同步收紧架构行数门禁。
- **潜在风险**
  - 大范围重排会与并行会话冲突；小步进行，每步先读最新文件。
- **验证指标**
  - 每轮拆分后运行 `npm run lint`、`npx tsc -b`、`cargo fmt --all -- --check`、`cargo clippy --workspace --all-targets -- -D warnings`。
  - 关键拆分后运行前端组件测试与 Core 协调器测试。

---

### SOL-09：性能回归门禁

- **适用问题类型**：持续性能退化防护。
- **预期收益**：把性能从“人工发现”变为“机器监控”。
- **实施优先级**：P1（与结构优化并行）。
- **落地步骤**
  1. 将 `synthetic_snapshot_history` 纳入定期回归，而不只是 ignored 手工测量。
  2. 为快照、watcher、扫描、SQLite 查询建立基线预算。
  3. 负载套件固定冻结 Worker 与合成数据，避免编译与测量并行。
- **潜在风险**
  - 基准抖动导致误报；需固定环境、多次采样、记录限制条件。
- **验证指标**
  - 每次变更产出 p50/p95/p99 与峰值内存 JSON，超过阈值阻断合并。

## 三、实施顺序

### 第一阶段：低风险快速收益（建议先做）

1. SOL-01 前端聚合进度引用修复。
2. SOL-02 进度监听生命周期重构。
3. SOL-04 第一步：`to_remove` 改 `HashSet` + 目录复用。
4. SOL-07 第一步：SFX 512KB 去重复读取。

### 第二阶段：结构优化（带基准）

5. SOL-03 快照分域缓存与增量投影。
6. SOL-06 SQLite 索引迁移。
7. SOL-09 性能回归门禁接入。

### 第三阶段：长期维护

8. SOL-05 最近历史增量索引。
9. SOL-08 超大模块拆分。
10. 建立快照、watcher、扫描、SQLite 的持续性能预算。
