## 1. 产品定位与核心设计哲学

### 1.1 产品定位
OpenUnpack 是一款面向 Windows 平台（x64）的**离线、开源、高性能批量解压与密码管理桌面软件**。它专为解决“多来源分散归档、带密码机械硬盘存储、多层嵌套打包、分卷混乱、老旧包文件名乱码”等真实痛点而设计。

### 1.2 四大铁律（Non-Negotiable Principles）
1. **绝对离线与隐私保护**：不设用户账户体系、不提供云端密码上传或联网查询、不采集任何遥测数据。密码库使用当前 Windows 用户级 DPAPI 进行硬件级加密保护，口令原文永不入库 SQLite、永不进入命令行参数或日志。
2. **原始数据安全第一**：默认始终保留源归档文件；任何临时解压产物在未通过最终完整性校验前不得呈现为成品；严禁静默覆盖或误删目标文件。
3. **基于确定性候选的精准匹配**：坚决不搞暴力穷举，仅在用户授权的“本地已存密码库 + 显式派生变体 + 可选离线常见语料”有限集合内做确定性轮试。
4. **性能为重、软硬协同**：将“解压验证”与“落盘提取”彻底分离，通过“首块轻量探针 + SSD 缓存流转 + 物理磁盘拓扑感知 + 协作式长驻 Worker”榨干硬件 I/O 与 CPU 效率，杜绝进程频繁 Spawn 与无效磁盘写。

## 3. 功能域详细设计规格（Functional Specifications）

### F1: 归档智能录入与扫描域 (Archive Ingestion & Scanning)

#### F1.1 录入方式与递归发现
- **操作方式**：
  - 支持拖拽单个文件、多个文件或整个目录树至软件主界面。
  - 支持“添加文件”与“添加文件夹”系统原生选择对话框。
- **扫描逻辑**：
  - 后台异步扫描，不卡死 UI 线程；支持万级目录树在 1 秒内完成遍历。
  - 自动过滤常见非归档大文件（如 `.iso`、`.vmdk`）与系统隐藏文件（如 `desktop.ini`、`Thumbs.db`）。
  - **输入排除规则**：支持按后缀（如 `*.url`, `*.txt`）或通配符排除文件，录入阶段提供实时匹配预览，避免无效排队。

#### F1.2 512 字节魔数深层嗅探 (Magic Bytes Sniffer)
- **业务场景**：识别被资源站恶意重命名伪装（如 `.mp4`、`.dat`、`.bin`、或去除后缀）的真实归档。
- **嗅探规则（前 512 字节扫描）**：
  - `7z`：`37 7A BC AF 27 1C`
  - `ZIP / ZIP-Multi`：`50 4B 03 04` 或 `50 4B 07 08`
  - `RAR 4.x`：`52 61 72 21 1A 07 00`
  - `RAR 5.x`：`52 61 72 21 1A 07 01 00`
  - `GZIP`：`1F 8B`
  - `BZIP2`：`42 5A 68`
  - `XZ`：`FD 37 7A 58 5A 00`
  - `TAR`：偏移量 257 处的 `75 73 74 61 72` (`ustar`)
  - `CAB`：`4D 53 43 46` (`MSCF`)
  - `ZSTD`：`28 B5 2F FD`
- **行为契约**：嗅探结果记录于任务元数据 `RealFormat`，**绝不物理篡改用户原文件的扩展名**，仅指导 Worker 选用对应解压内核。

#### F1.3 工业级分卷成组与断卷自愈 (Volume Grouping & Integrity Check)
- **支持命名范式**：
  - 7-Zip 风格：`.7z.001`, `.7z.002`, ...
  - WinRAR 新风格：`.part1.rar`, `.part2.rar`, ...
  - WinRAR 旧风格：`.rar`, `.r00`, `.r01`, ...
  - PKZip 分卷：`.z01`, `.z02`, ... `.zip`
- **成组规则**：自动归拢同组分卷为单一逻辑任务条目，列表仅展示“首卷/主卷”，并展示分卷总数与跨卷总物理大小。
- **断卷防御**：若缺少第 1 分卷，任务直接标记为 `MissingFirstVolume`（阻断状态）；若中间缺卷，标记 `BrokenVolumeSequence` 并标红指出缺失卷序号，禁止盲目启动造成 I/O 浪费。

### F2: 密码保险库与候选流水线域 (Vault & Candidate Pipeline)

#### F2.1 密码库安全存储与组织
- **持久化架构**：存储于 `%LOCALAPPDATA%\OpenUnpack\vault.dat`，整库经当前 Windows 账户的 DPAPI（`DataProtectionScope.CurrentUser`）加锁保护。
- **数据模型**：
  - 密码实体：`PasswordId (UUID)`, `Text (明文口令)`, `GroupId`, `Note (备注)`, `Tags`, `Enabled (布尔)`, `SuccessCount (命中计数)`, `LastUsedTime`。
  - 分组管理：默认支持“全部”、“常用”、“网站/论坛”、“自定义分组”，支持一键全选禁用/启用某个分组。
- **导入/导出机制**：
  - **批量导入**：支持 TXT（一行一个）和 TSV（名称、口令、分组、备注）。导入前进行双向比对去重预览，并提示新增与冲突项。
  - **安全备份**：支持导出为加密备份文件（`.opuvault`），强制用户设定独立高强度备份口令（采用 Argon2id/PBKDF2-SHA256 200,000 次迭代 + AES-256-GCM 封装）。

#### F2.2 候选流水线与来源溯源 (Candidate Pipeline & Provenance)
- **流水线抽象（拉取式）**：
  ```csharp
  public interface ICandidateSource {
      IAsyncEnumerable<CandidateLease> GetCandidatesAsync(ArchiveNode node);
  }
  ```
- **候选源分层优先级**：
  1. **强关联记忆命中**：若该文件内容 Hash 在 SQLite 历史中有成功匹配记录，优先推入队列头部。
  2. **激活分组密码**：根据用户选中的分组范围，按 `SuccessCount` 降序推入。
  3. **规则派生候选（可选开启）**：
     - 去除首尾空格变体（保留库中原值，增加派生项）。
     - 大小写变体（如全小写、全大写）。
     - 归档文件名提取（识别形如 `[pwd-123456]filename.zip` 的嵌入口令）。
  4. **离线内置常见语料（可选开启）**：随安装包携带的公开合法高频通用口令表（纯离线本地只读）。
- **来源租约契约（防脏写与安全审计）**：
  - 每个下发的测试口令封装为 `CandidateLease`，必须携带 `CandidateOrigin` 标示：
    `{ Original | TrimmedSpaces | CaseVariant | FromFileName | Corpus }`
  - **铁律**：派生口令即使成功，也绝不能直接静默篡改覆盖保险库的原始口令条目；在生成任务结果时明确标出：“通过派生口令[xxx]匹配成功”。

### F3: 极速探针与双层解压引擎域 (Password Probe & Extraction)

#### F3.1 极速轻量探针层 (Password Probe - P0 核心优化)
- **设计初衷**：彻底颠覆传统工具“试一次密码就执行一次全量解压”的低效做法。探针层**零落盘、不建目录、不解压实体文件**。
- **探针分级实现**：
  | 归档格式 | 加密机制 | 探针判定原理 | 单次探测耗时 |
  |---|---|---|---|
  | **ZIP (Traditional)** | ZipCrypto | 读取 12 字节加密头，校验 CRC32 检查字节 | **< 1 μs** (纯内存位移) |
  | **ZIP (AES-256)** | WinZip AES | 解密 2 字节 Password Verification (PV) 标识 | **< 5 μs** |
  | **7z (AES-256)** | 7z Crypto | 仅解压头数据块或首个文件前 16 字节，验证 HMAC | **~ 20 μs** |
  | **RAR 5.x** | PBKDF2 + AES | 验证 PSWCheck 字节校验块，匹配失败直接退出 | **~ 50 μs** |
  | **固实压缩包 (Solid)** | 连续数据流 | 读取第一分片前 4KB 数据尝试解包判定 | **~ 1-5 ms**（降级为可控探测） |
- **容错防线**：若探针通过（ZipCrypto 存在 1/256 假阳性），交由正式解压管道；若正式解压因密码失败，探针回退并拉取下一个候选，杜绝误判。

#### F3.2 独立长驻解压 Worker 架构
- **隔离进程模型**：
  - Rust Core 通过 Windows Job Object 管理独立 `.NET 10 Worker` 进程。
  - 进程长驻运行，通过命名管道（Named Pipe）持续接收 `Inspect / Probe / Extract / Cancel` 指令，彻底消灭外部进程反复 `Process.Start` 产生的 10~30ms 系统开销。
- **崩溃与死锁自愈（Watchdog）**：
  - 双心跳保活机制：管道无数据传输静止超时达到 120 秒，看门狗触发非阻塞状态探测。
  - 若引擎底层（原生 C++ dll）陷入死循环，Job Object 直接强制终止 Worker 进程，Core 捕获崩溃并标记 `WorkerUnresponsive`，立即拉起新 Worker 恢复队列，**主程序永远不卡死、不闪退**。

#### F3.3 双层嵌套自动展开机制 (Archive-in-Archive)
- **多层递归处理流程**：
  1. 第一层归档解压至 SSD 暂存区：`workspace/nodes/{nodeId}/`。
  2. 提取器在输出流中实时嗅探是否存在内部压缩包（如 `.7z`, `.rar`, `.zip`）。
  3. 若配置了“自动展开内包”，针对内层文件创建子任务节点 `ChildNode`，进入专属候选密码尝试流水线（**支持内外层密码完全不同**）。
  4. 最终写回目标盘时，根据“内层归档保留策略”：
     - *默认策略*：展开内包内容，物理释放内层临时压缩包，避免双重占用磁盘。
     - *保留内包*：成品同时保留原始内包与展开后的文件夹。

### F4: 编码智能识别与乱码自愈域 (Encoding Self-Healing)

#### F4.1 乱码成因与智能评分探测
- **痛点场景**：ZIP 规范在 2006 年前未强制 UTF-8，大量中文（GBK/GB18030）、日文（Shift-JIS）、繁体（Big5）历史老包在现代系统解压时必然出现乱码甚至非法文件名导致写入失败。
- **探测矩阵与启发式评分算法**：
  - 读取 ZIP Local File Header / Central Directory，若 General Purpose Bit 11（UTF-8 flag）未置位：
    1. 提取文件名原始字节流 `byte[]`。
    2. 分别代入 `UTF-8`、`GB18030`、`Shift-JIS`、`Big5` 解码。
    3. **双字节语义有效性评分**：
       - 检查汉字/假名高频字区间命中率（如 GBK 常用字区间 `0xB0A1 - 0xF7FE`）。
       - 严厉惩罚不可见控制字符、全角半角混杂错乱、替换字符 `\uFFFD`。
    4. 自动选用最高评分编码进行目录结构重构。

#### F4.2 路径安全净化与无损重试
- **路径安全净化（Path Sanitization）**：
  - 拦截所有路径遍历攻击（`../` 或 `..\`）。
  - 剥离 Windows 保留设备名（`CON`, `PRN`, `AUX`, `NUL`, `COM1-9`, `LPT1-9`），自动重命名为安全替代名。
  - 规范化长路径格式，全面支持 `\\?\` 前缀与 UNC 路径（`\\?\UNC\`），突破 260 字符限制。
- **无损编码重试**：若用户发现解出文件名仍有轻度偏差，系统允许在记录中“切换编码重新写回”——由于已在 SSD 保留解压提取缓存，**无需重新读取源包与密码破解，可在 1 秒内完成瞬时重构**。

### F5: 存储流转与拓扑感知调度域 (Storage & Topology Scheduling)

#### F5.1 物理磁盘拓扑感知引擎 (Device Topology Provider)
- **设计原理**：机械硬盘（HDD）的并发随机读写会导致磁头剧烈寻道，吞吐量断崖式下跌（150MB/s → 5MB/s）。而普通盘符（`D:`, `E:`）完全可能属于同一块物理磁盘。
- **底层拓扑探查**：
  - 调用 Win32 `QueryDosDeviceW` 与 `DeviceIoControl(IOCTL_STORAGE_GET_DEVICE_NUMBER)` 映射卷到物理盘 `\Device\HarddiskN`。
  - 检测介质类型（HDD 机械旋转 / SSD 固态闪存）。
- **调度调度契约**：
  - **同一物理 HDD 严格串行**：同一时刻对同一块物理 HDD 仅允许一个任务执行 I/O 读取。
  - **不同物理盘并行并发**：HDD 读源包 -> SSD 缓存解压 -> 另一块目标盘写回，三者完全异步重叠（Pipelining）。
  - **拓扑探测失败保底**：若因虚拟机或精简系统权限无法探测，保守降级为全局串行，绝不产生 I/O 争用风暴。

#### F5.2 SSD 高速缓冲流转生命周期
```
[ 源盘 HDD ] ────(顺序大块直读)───► [ SSD 工作缓存区 ]
                                           │
                                  (首块探针 + 极速解密)
                                           │
                                    [ 解压输出临时区 ]
                                           │
                                    (流式 SHA-256 计算)
                                           │
[ 目标盘 ] ◄───(校验无误顺序写回)───────┴─── (封存不可变清单)
```
- **工作区租约与空间预算**：
  - 设定 SSD 缓存警戒线（默认保留 20 GB 物理剩余空间）。
  - 每个解压任务必须先申请 `StorageReservation`，配额超额时对扫描队列施加反压（Backpressure），等待前序任务释放。
  - 任务一旦成功发布，SSD 临时中间层立即安全回收。

### F6: 任务生命周期、状态机与事务发布 (Lifecycle & Publication)

#### F6.1 12 态任务全生命周期状态机
任务状态由 SQLite 单一写入者保证 ACID 事务流转：

| 状态值 | 语义说明 | 用户可见提示 |
|---|---|---|
| `Queued` | 任务已建立，等待 I/O 物理盘许可 | 排队中 |
| `ProbingPassword` | 正使用探针高速试错候选口令 | 正在匹配密码 (N/Total) |
| `ExtractingToCache`| 密码已匹配，正在 SSD 展开数据 | 正在解压至缓存 (XX%) |
| `ExtractingInner` | 正在解压内部嵌套归档 | 正在展开内层包 (层级: 2) |
| `VerifyingStream` | 流式计算摘要并比对引擎校验码 | 正在校验完整性 |
| `Publishing` | 将已验证结果顺序复制并重命名至目标盘 | 正在发布到目标位置 |
| `Success` | 最终交付完成，记录历史 | 解压完成 |
| `PartialSuccess` | 外层成功，内层因缺密码/损坏保留未展开文件 | 部分完成（含未展开内包） |
| `PasswordNotFound`| 遍历所有候选及派生规则均未命中 | 密码不匹配（已试 N 个） |
| `DamagedArchive` | 压缩包 CRC 校验不通过或文件头受损 | 压缩包损坏 |
| `DiskFull` | 目标盘或 SSD 缓存磁盘空间耗尽（暂停熔断）| 磁盘空间不足（可清理后继续） |
| `Cancelled` | 用户手动取消（安全停止 Worker 并回收临时文件）| 已取消 |

#### F6.2 原子发布与崩溃断点恢复机制 (Two-Phase Publishing)
- **两阶段发布保证**：
  1. *暂存阶段*：将文件以 `.openunpack-tmp-{publishId}` 临时目录形态写向目标卷。
  2. *提交阶段*：写入不可变控制签名 `publish-marker.json`，在目标卷内部执行瞬时改名（`MoveFileEx` 原子重命名），完成最终落地。
- **崩溃孤岛自愈**：
  - 若解压过程中发生断电或强关，软件下次启动时扫描各工作区。
  - 依赖 SQLite 记录与工作区 `workspace-owner.json` 核对：
    - 未发布成功的临时残留目录，自动归拢并弹出“异常中断清理向导”。
    - 已经校验完成但尚未改名的成品，允许用户一键“断点继续发布”，无需重新花费数小时解压。

### F7: 守护机制与系统交互域 (System Guardians & Observability)

#### F7.1 现代 Windows 电源唤醒锁 (Power Request Guardian)
- **机制原理**：长时间批量处理几百 GB 压缩包时，避免被 Windows 自动睡眠切断。
- **实现方案**：
  - 使用 Windows Vista/7/10/11 官方推荐的 `PowerCreateRequest` + `PowerSetRequest(PowerRequestSystemRequired)`。
  - 任务队列运行时主动锁定系统睡眠；队列完成、暂停、用户手动取消或进程崩溃时自动释放。
  - 提供用户偏好设置：“批量任务期间阻止电脑休眠（默认开启）”。

#### F7.2 大文件清单安全落盘回传机制 (Manifest Spill)
- **保护场景**：应对包含数万至数十万小文件的超大归档（如开发源码包、游戏资源包），防止一次性回传击穿 IPC 内存或触发 8MB 管道截断。
- **机制逻辑**：
  - Worker 在内存中构建文件清单，一旦预估大小超过安全阈值（8MB - 64KB），自动转为流式落盘至 `nodes/{nodeId}/manifest.json`。
  - 管道仅回传微型事件：`{ event: "Completed", manifest_path: "C:\\...\\manifest.json" }`。
  - Rust Core 零延迟分块反序列化并立即销毁临时 JSON，内存开销恒定受控于 10MB 以内。

#### F7.3 平滑速率与智能 ETA 评估 (Moving Average ETA)
- **算法模型**：采用指数加权移动平均（EWMA）计算实时瞬时与长周期加权 I/O 速率，平抑解压零散小文件时速率疯狂跳动的问题。
- **固实包免惊扰**：针对固实压缩包大块解码初期“无文件输出”的状态，状态栏显示“正在高速解码数据块...”，暂时抑制 ETA 计算，杜绝呈现“剩余 999 小时”的荒谬现象。

## 5. 验收标准与测试契约 (Acceptance Criteria)

为保障工程交付品质，各项核心设计必须通过以下自动化集成与场景验证：

1. **探针验证隔离性**：
   - 用例：在 100 个候选密码中设置只有最后一个正确。
   - 验证：前 99 次探测不得触发任何文件落盘、磁盘写入量为 0，平均每次探测耗时小于 100 微秒。
2. **文件名编码无损转换**：
   - 用例：输入使用 GBK 压缩的含中文特殊字符归档，以及 Shift-JIS 压缩的日文归档。
   - 验证：解压后绝对不得出现 `锟斤拷` 或 `???`，文件名评分系统自动命中对应字符集且日志记录确切转换置信度。
3. **分卷容错阻断**：
   - 用例：输入缺失 `.part2.rar` 的 RAR 分卷序列。
   - 验证：任务在扫描排队阶段被拦截，明确告警 `MissingVolume: part2`，不进入解压阶段。
4. **大清单无死锁与溢出**：
   - 用例：输入解压后包含 100,000 个文件的归档。
   - 验证：IPC 清单落盘机制触发，管道无丢包，Worker 与 Core 内存峰值稳定在 150MB 以下。
5. **休眠唤醒与看门狗恢复**：
   - 用例：模拟系统挂起/休眠事件，或人工注入线程假死。
   - 验证：休眠期间不触发超时死锁误判；真正假死达到 120 秒看门狗阈值时成功执行强杀并安全拉起新 Worker。
