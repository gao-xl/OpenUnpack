# OpenUnpack 现代架构与 UI 规范

版本：0.3 新主方案讨论稿 · 2026-10-08 · 状态：仅设计，尚未实现或通过运行验收

用户已要求：Windows 优先、独立开源、密码管理与批量解压、机械硬盘来源的 SSD 缓存、双层解压、降低校验耗时、Windows 账户自动解锁密码库，以及现代化 UI 库、完整功能分类、UI 由 Gemini 设计。应用代码编辑继续停止。

本稿推荐 Tauri 2 + React/TypeScript + Ant Design + Rust 本地核心 + 独立作业进程（解压 Worker / 传输 Worker）。长时缓存复制、写回和目标回读也进入隔离进程，避免仅给主进程中的阻塞线程加超时。框架选择仍是可评审的推荐，并非用户已逐项确认。旧 architecture.md 0.1 的 WPF 方案保留作比较；已有 C# 骨架不是本稿的实现。本稿与旧稿冲突处，以下面的设计规则为新建议。

## 1. 范围、决定与边界

首版包含：密码分组/搜索/导入/备份、有限候选轮试与成功关联、递归扫描/分卷、队列、可选内包展开、SSD 工作目录、标准验证/完整目标回读、输出冲突处理、历史与恢复。

密码、文件与任务默认留在本机。云账户、收费查询、穷举、跨平台验收与工具箱候选不进入首版。静态设计稿可展示示例任务；实际首屏必须是真实空队列。

| 决定 | 推荐答案 | 确认状态 / 下一道验收 |
|---|---|---|
| 桌面路线 | Tauri 2 + React/TypeScript，界面与本地核心分离 | 推荐；实现恢复后做原生交互与离线安装 PoC |
| UI 库 | Ant Design，统一主题与组件包装；由 Gemini 负责页面设计 | Gemini 提案，主 agent 已核对 Table/主题官方资料；不混搭第二套主组件库 |
| 本地核心 | Rust 模块化单体；异步协调与有界后台执行 | 推荐；文件、密码与状态权限集中在本地核心 |
| 隔离作业 | 解压 Worker + 官方 7-Zip 适配器；传输 Worker 执行长时复制/回读 | 首版架构建议；密码回调/流式摘要/取消与真实退出确认先验证 |
| 初始并发 | 单根任务；按物理盘预留调度接口 | 默认建议；多盘并行需性能与故障验收 |
| 存储 | SQLite 任务状态 + 账户保护密码库 + 不可变结果清单 | 推荐；不能宣称多个存储共享原子事务 |
| Windows 范围 | Windows x64 优先 | 最低系统构建、WebView2 版本与依赖精确版本在 PoC 后锁定 |
| 可调默认值 | 双层展开、20 GiB 缓存建议、历史保留量 | 均为建议；配额、阈值、保留期限不视为用户已确认 |

设计由主 agent 负责系统边界与复核；Gemini 负责 UI 库提案、信息架构与页面布局。当前没有需要用户批准才能继续撰写的事项。恢复应用实现必须由用户明确提出。

## 2. 为什么推荐这条路线

现代化体现为：统一组件体系、界面与业务解耦、版本化协议、可持久化任务状态、受资源预算约束的处理管线，以及明确的发布和恢复规则。

Tauri 允许 Web 界面与 Rust 本地核心通信，在 Windows 使用 WebView2。实际 WebView 可能创建多个系统进程，因此这里划分的是三类进程角色，不承诺系统进程总数为三。[Tauri 进程模型](https://v2.tauri.app/concept/process-model/)

| 路线 | 适用理由 | 实际代价 |
|---|---|---|
| Tauri 2 + React + Rust（主方案） | 可使用完整现代 Web 组件，Gemini 易于围绕统一组件设计页面；业务接口为未来平台适配留边界 | WebView2 安装/版本管理、TypeScript 与 Rust 维护、额外原生引擎桥接；不因此承诺解压更快 |
| WinUI 3 + .NET（原生备选） | Windows 原生交互与微软桌面技术路线 | 需要 XAML 设计和 Windows App SDK 部署验收；未来平台适配成本不同 |
| WPF + WPF UI（增量备选） | 可承接已有早期 C# 工作，已有成熟桌面控件经验 | UI 方案依赖社区库；业务可靠性仍须独立设计 |

WPF 仍有 .NET 10 更新，WinUI 3 是微软面向新 Windows 应用推荐的原生框架；选择主方案的理由是产品与设计方式的匹配，不是宣称另外两条路线停止维护。[WPF 更新](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/whats-new/net100)、[Windows UI 框架选择](https://learn.microsoft.com/en-us/windows/apps/get-started/choose-framework)

## 3. 系统边界和所有权

    React / Ant Design 界面
        ↓ 类型化用户命令 ↑ 脱敏快照 / 阶段事件
    Tauri Rust 本地核心
        ├─ 扫描与分卷服务
        ├─ 任务状态机 / 物理磁盘调度器
        ├─ 密码候选 / 账户保护保险库
        ├─ SSD 工作区 / 存储预算
        ├─ 结果规划 / 验证 / 发布 / 恢复
        └─ SQLite 单写入者 / 成功事件 outbox
        ↓ 私有版本化 IPC ↑ 进度 / 结果清单
    独立作业进程（按操作启动）
        ├─ 解压 Worker：原生适配层 → 官方 7-Zip 引擎
        └─ 传输 Worker：源缓存 / 写回临时目录 / 目标回读

界面拥有显示状态、筛选、选择、展开和对话框状态；不拥有任务完成判定。Rust 核心独占任务数据库、保险库和最终发布决定。解压 Worker 只处理获准源包/分卷组并写当前尝试目录；传输 Worker 只执行核心批准的文件映射，在工作区或目标卷临时目录写入并返回摘要/回读结果。两者不读取整库、不写任务数据库、不决定或执行最终发布改名。

独立进程提供故障隔离；若没有额外受限令牌或沙箱，Worker 仍有当前用户权限。Tauri 的前端 capabilities 也不自动约束本地核心自己的代码。[权限边界](https://v2.tauri.app/security/capabilities/)

## 4. 业务模块与契约

| 模块 | 职责 | 主要契约 |
|---|---|---|
| ScanService | 递归发现、路径去重、分卷归组、容器排除 | 来源选择 → SourceGroup；分页扫描结果 |
| JobCoordinator | 根任务、节点和尝试的状态转移 | JobOptionsSnapshot、操作 ID、阶段事件 |
| ResourceScheduler | 来源/工作/目标物理盘以及 CPU/内存预算 | 一次取得一组 I/O 许可，避免分开持锁等待 |
| PasswordResolver | 分组范围、启停、关联优先、候选去重 | passwordId + passwordRevision → 单次敏感租约 |
| VaultService | 账户保护、导入事务、编辑、备份和恢复 | 脱敏条目视图；显式口令编辑/查看命令 |
| WorkspaceManager | 归属、预留、实时占用、释放和残留目录 | WorkspaceLease、StorageReservation |
| EngineClient | Worker 生命周期、协议、错误映射 | Inspect / Extract / Cancel |
| TransferClient / WorkerSupervisor | 缓存复制、目标临时目录写回、目标回读与进程监视 | CopyAndDigest / Readback / Cancel；操作 ID 与批准路径范围 |
| NativeArchiveAdapter | 原生打开、条目预检、密码回调、提取、摘要 | ArchiveNode → NodeResultManifest |
| ResultPlanner | 合并内外层映射，保留普通文件和未展开内包 | FinalResultManifest；不额外复制一份 SSD 成品树 |
| VerificationService | 引擎检查、复制源流摘要、可选目标回读 | 可区分的验证范围与结果记录 |
| Publisher | 目标卷临时目录、冲突、改名提交 | PublishIntent → PublishReceipt |
| JobRepository / RecoveryService | 状态保存、异常窗口恢复、记录 | SQLite 单写入者、恢复动作、成功 outbox |

领域规则不依赖 React、Tauri、SQLite 或原生引擎。适配器实现领域/应用端接口，装配点注入具体实现。工具箱未来以用例模块扩展；首版不开放任意第三方代码加载。

## 5. 两条通信边界

界面到核心使用少量类型化命令：scan_sources、create_job、start_jobs、pause_jobs、cancel_jobs、retry_node、query_jobs、query_history、import_passwords、backup_vault、recover_publication。参数和错误用版本化 DTO；由同一契约生成或校验 Rust/TypeScript 类型，并在运行时检查格式、长度、权限和操作前置条件。

命令返回操作 ID 或分页视图；进度通过数据通道合并推送，阶段与错误及时通知。普通进度建议每 100–200 ms 更新一次，阶段事件不必等待刷新周期。界面重新连接时先拉当前快照，再消费更高序号的事件，不能只靠漏失的通知重建任务状态。[Tauri 命令与数据通道](https://v2.tauri.app/develop/calling-rust/)

界面只收到文件引用和显示元数据，不经前端传递压缩包内容。源与目标由本机选择/拖放入口取得，再由核心规范化并校验。文件夹拖放不得按普通网站 Upload 组件上传到服务器。

capabilities 和应用自定义命令权限均须显式限制：注册自定义命令默认可调用，不应认为只配置插件权限就已保护它们。Rust 命令还须做调用窗口、授权文件范围和任务归属检查。前端不获任意 shell、数据库、文件读写或 Worker 启动能力；界面资源随应用打包，限制远程导航及脚本来源。

核心到 Worker 使用当前用户受限的私有本地管道；检查预期子进程身份、协议版本、requestId、jobId、nodeId、attemptId、publishId（适用时）和运行代次。请求规定源组或不可变复制映射、批准写入根、预算；过期消息不得推进新尝试。控制与数据使用独立接收路径，取消不能排在大清单或进度后。消息有长度限制，海量条目分批输出或落成核心验证的清单。

口令一次只传当前候选，进入原生密码回调；不进入命令行、环境变量、任务库、结果清单或日志。可采用官方引擎的薄原生 ABI 桥；不能简单把 CLI 的密码参数包装成安全方案。桥接、增量摘要和取消回调是否可用，是早期 PoC 的硬验收项。

## 6. 持久化状态机与任务树

分别记录任务、节点、尝试、发布和清理状态。控制意图（运行/暂停/取消）与当前阶段分开，避免用一个状态字符串混合业务阶段与操作请求。

    排队 → 来源检查 → 资源预留 → 可选源缓存
      → 外层解压 → 内层处理 → 封存结果清单
      → 写回目标临时目录 → 所选验证 → 发布 → 完成

需要密码、空间不足、缺卷与 Worker 故障有明确等待/失败分支；取消先进入“正在取消”。每个关键转移定义前置条件、持久化顺序和幂等操作 ID。瞬时进度不逐字节写 SQLite。

每个 RootJob 可含多个 ArchiveNode，节点有独立密码、尝试和结果。只重试失败节点，创建新 Attempt。所有选定节点完成且发布成功，根任务才计为全部完成；部分交付必须显式选择，清单保留未展开内包与原因，不自动显示“全部成功”。

根任务配置冻结，密码库仍可原子编辑；当前敏感租约不随编辑改变，新尝试遵循记录版本/启停规则。passwordRevision 在口令内容改变时递增，与名称/备注等元数据版本区分。补密码只受控刷新等待节点的候选快照，不更改正在写回的封存结果。用户删除或改动口令后，迟到成功事件不得重建条目或把旧成果关联到新口令。

## 7. SSD 管线与磁盘调度

按需缓存完整源包/分卷组；外层和内层都在工作区处理。最终清单把每个输出相对路径映射到其节点结果文件；Publisher 按不可变映射驱动传输 Worker 从这些文件顺序写入目标卷临时目录，核心审核传输/验证结果并独占最终改名决定。正常完成路径不额外生成第三份 SSD 合并目录，不把中间层写回 HDD。

预算分开统计：实时占用 + 未消耗预留 + 必须保留空间。预留转成实际占用时扣掉相应预留，不能重复计算。失败尝试和等待工作区也占配额。未知展开大小采用有界增量额度并监测真实可用空间，超限进入可恢复等待状态。

同一物理 HDD 默认只允许一个活跃读写阶段；不同盘符不等于不同物理盘。每个阶段一次申请涉及的整组许可；拓扑不明时保守串行。SSD、CPU、内存有各自预算，队列有界并施加背压。首版可先单根任务，保留多盘扩展接口。

只有无活跃读者、无最终清单引用、能够从保留来源重建的中间文件才允许释放。清理同时验证数据库归属与工作区标记，不跟随链接清理到工作区之外。源盘和目标盘若同为一块 HDD，先完成该任务解压，再顺序写回，避免争用。

## 8. 校验范围与速度

解压输出时增量计算 SHA-256，并记录引擎可提供的 CRC/MAC 等结果；整节点成功后封存不可变清单。摘要绑定 nodeId、attemptId、文件版本、路径和大小。该摘要证明与本次解码结果的一致性，不证明来源真实性。

标准模式：从 SSD 读取并写向目标时同步计算源流摘要，与封存摘要比较，同时检查读写/关闭错误和文件数量/大小。界面显示“标准验证完成；未完整回读目标”，不把源流摘要称作目标盘内容证明。

完整回读模式：写完后完成要求的刷新，重新读取目标文件并比对摘要，再发布。记录实际读取方式；普通回读可能由系统缓存满足，不能未经验证显示“已绕过缓存”或“保证断电不丢失”。设备、文件系统和缓存行为另行验收。

完整源包指纹、采样指纹、元数据指纹类型不同。强密码关联只接受完整内容指纹；分卷组按确定的卷顺序、长度和完整卷摘要规范编码整组指纹，不能只用首卷摘要。尽量在必要源包复制时取得，不为记忆功能强制再扫描一次整个 HDD。输出摘要不能冒充源包 SHA-256。

常规流程保留路径/条目预检，避免完整 test 与完整 extract 重复解码。固实压缩、CPU 解码、文件创建和最后 HDD 写入仍会耗时；框架更换不等于解压吞吐提升。

## 9. 存储与恢复提交点

| 存储 | 内容 | 规则 |
|---|---|---|
| tasks.db | Jobs、Nodes、Attempts、Workspaces、Publications、成功 Outbox、SchemaVersion | SQLite 是任务可变状态唯一权威；核心单写入者；无口令 |
| vault.dat | 密码、分组、备注、统计、强关联和已应用事件 ID | 当前用户 DPAPI 全库保护、原子替换；失败禁止明文降级或空库覆盖 |
| settings.json | 全局默认值、格式版本 | 无口令，任务开始时生成配置快照 |
| 不可变清单 | 节点结果、最终路径映射、摘要、验证能力 | 文件/证据描述，不存可变任务阶段；数据库保存引用和清单摘要 |
| 迁移备份 | 保险库可迁移内容 | 独立口令、版本化容器；沿用 PBKDF2 + AES-GCM 草案，参数在实现前验证锁定；先验证后合并 |

DPAPI 使用当前用户范围，不使用机器范围。备份口令与 Windows 账户绑定解锁相互独立。[DPAPI 文档](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)

发布流程：持久化 publishId 与目标意图 → 在目标卷创建独立临时目录 → 复制并验证 → 记录可核对的归属标记和准备状态 → 处理冲突并进行同卷非覆盖改名 → 在 SQLite 事务中提交发布状态和成功 outbox → 独立清理 SSD。

目标名称变更先更新发布意图，再改名；改名成功是交付边界，之后取消不得删除成品。跨卷复制、目录改名、SQLite 和保险库不是同一个原子事务。已改名未记库时，恢复核对发布意图、清单和可信归属后补记；无法确认时等待处理，不凭目录存在认定成功。[SQLite 提交边界](https://www.sqlite.org/atomiccommit.html)

成功事件携带 passwordId + passwordRevision，不含口令。保险库仅在记录仍存在且口令版本匹配时，按 eventId 幂等应用统计和强关联，再确认 outbox；崩溃重放不重复计数。记录已删除、口令已改变或版本无法匹配时，跳过关联并确认该事件，保留文件交付成功；不能把旧口令成果关联给新口令。文件已交付但库保存失败，显示独立提示，不回滚成品。

| 中断位置 | 恢复规则 |
|---|---|
| 提取未结束 | 未完成 Attempt 失效；确认 Worker 退出后清理或重新尝试 |
| 节点封存、内包缺密码 | 验证归属与所复用文件摘要后，仅重试等待内包 |
| 写回中 | 临时输出不算成品；验证 SSD 结果后重新写回 |
| 准备发布或改名后未记库 | 核对意图、目标冲突、归属与必要内容证据后继续/补记 |
| 成品已发布、清理失败 | 保留成品，清理独立重试 |
| 归属或结果证据不匹配 | 进入待处理；不覆盖或删除无关目录 |

取消先协作，超时终止 Worker 及子进程，确认退出和句柄关闭后清理。主进程用 Windows Job Object 等机制约束子进程生命周期；主进程退出后不留继续写入的失控 Worker。异常退出清理由下一次恢复完成。

## 10. Gemini UI 提案与复核后的信息架构

Gemini 已只读阅读两份现有规范，并推荐 Ant Design。已核对其 Table 虚拟滚动、筛选/排序及主题能力；树形嵌套与虚拟滚动组合、大量进度刷新和无障碍表现仍需真实桌面验收。Input.Password 只提供遮盖交互，不自动提供保险库加密。[Ant Design Table](https://ant.design/components/table/)、[主题](https://ant.design/docs/react/customize-theme/)

| 主分类 | 全部子功能及入口 | 布局 / 组件归属 |
|---|---|---|

## 15. 错误处理、防死锁与无进展处置

本节为首版可靠性规范。目标是发现、限制和恢复异常，不承诺不存在任何死锁或系统级 I/O 卡死。错误、无进展、资源等待和循环死锁分别记录；心跳仅证明监视路径还能回应，超时仅触发处置，不证明根因。

### 15.1 错误分类与重试规则

| 情况 | 影响范围 | 规定动作 |
|---|---|---|
| 需要密码 / 候选耗尽 | 当前节点 | 继续有限候选或进入待密码；不自动生成口令，不把含歧义的引擎结果强判为密码错误 |
| 坏包、缺卷、校验不符、不支持格式 | 当前节点 | 明确原因，保留源；等待补卷/新源/设置改变后创建新 Attempt，不原样无限重试 |
| 缓存满、目标满、设备不可用 | 对应物理盘与依赖任务 | 协作停到可确认边界，释放临时执行许可；保留文件仍计入占用，提示换位置/配额/清理后再试 |
| 短暂文件占用、可确认未提交的数据库繁忙 | 当前操作 | 有界退避重试；次数、总等待期限和取消均受预算限制 |
| 解压/传输进程崩溃、协议错误、失联 | 当前操作及占用资源 | 使代次失效，监视并停止进程；实际退出确认后重试新进程/新操作；不能复用半完成 Attempt |
| SQLite 无法写入、保险库损坏/账户解锁失败 | 对应持久化能力 | 暂停依赖它的新状态变更与发布；保留原数据和最后确认状态，仍允许独立停止路径，不新建空库覆盖 |
| 发布改名或数据库提交结果不明 | 当前 Publication | 进入发布待核对；先核实意图、归属和提交点，不盲目重写/删除目标 |
| 清理失败或成功记录保存失败 | 后处理 | 文件完成状态保留，显示独立提醒；清理/outbox 幂等重试，不重新解压成品 |
| 内部不变量失败 / 核心 panic | 核心任务调度 | 停止新调度和不可逆操作，尽力停止已启动作业，保存可用的脱敏诊断；重启后按持久化证据恢复，不带不可信状态继续 |

重试分为：同一幂等操作的重发、新 Attempt 的重试、状态修复后的续接、禁止自动重试。每种错误绑定允许动作，不由 catch-all 统一重试。自动重试采用有界退避及最大次数/总期限；具体数值在 PoC 后锁定。新 Attempt 有新目录和代次；同一发布请求先按 operationId 查询/核对是否已生效，再决定重发。

错误契约含 errorCode、scope、stage、jobId/nodeId/attemptId/publishId、operationId、generation、最后确认提交点、retryClass、允许恢复动作和脱敏说明。原始异常不直接传界面或日志；不含口令、管道敏感载荷或完整进程内存。数据库不可写时不能宣称新错误状态已成功落库。

### 15.2 防循环等待的强制规则

1. 状态由明确的单写入者管理，通过消息交互；Mutex/RwLock 只保护短内存操作。本项目不持状态锁跨 await、不持锁做文件/数据库 I/O、不持锁等待另一个组件或 Worker 回应。确需多锁的局部结构使用统一顺序，优先消除嵌套锁。[Tokio 共享状态](https://tokio.rs/tokio/tutorial/shared-state)
2. 协调器把长时操作交给执行器，接收带操作 ID 的完成消息；消息处理回合不等待整个解压/复制结束。数据库写入者、保险库与资源调度器不同步回调并等待协调器；SQLite 事务中不等待 Worker、用户操作、保险库或文件发布。
3. 物理盘、Worker 槽位、CPU/内存的临时执行许可，由统一准入机制一次授予整组；拿不全就排队，不保留部分许可等待另一项。许可归属于操作代次，只有真实停止/完成后才释放；结果文件引用和已占空间不是执行许可。
4. 外层阶段结束、封存结果后，先释放 Worker 与 I/O 许可，再调度子节点。根任务等待内包时只保留状态和必要文件引用，子节点不等根任务完成。不能让父任务占着唯一 Worker 等待子任务。
5. 展开额度增长被拒时，不占着执行名额无限等待空间。协作停止并确认句柄状态后释放临时许可，保留文件继续计入占用，进入空间不足。若下一阶段最低工作额度已不可行，明确需要调整位置/额度/清理，不能等待只能由本任务完成后释放的空间。
6. 控制通道与结果数据通道分离：控制接收器负责取消、探测和退出；数据接收器持续排空，即使 UI 未订阅也不能停止接收。普通进度可合并丢旧快照；结果、错误和终止状态不能静默丢弃。结果通道失败时使当前操作进入故障/待核对，不让工作进程无限阻塞发送。

典型死锁：唯一 Worker 槽位被外层父任务持有，父任务等待内包；内包又等待该槽位。增加等待超时不能替代第 4 条的结构修正。

SQLite 使用短事务、单写入者和分页短读取；busy_timeout 只承担有界锁等待，不作为死锁预防。区分 BUSY、BUSY_SNAPSHOT、LOCKED、FULL、IOERR、CORRUPT。旧快照升级写入失败先释放/回滚旧事务并重新校验状态；数据库错误不能都归为可重试繁忙。[繁忙等待](https://www.sqlite.org/c3ref/busy_timeout.html)、[隔离与快照](https://www.sqlite.org/isolation.html)

### 15.3 监视、超时和真正退出

WorkerSupervisor 的计时/进程监视与作业数据消费分开，控制路径不依赖普通进度队列或 SQLite 完成。监视记录：进程存活、最后控制回应、最后引擎检查点、最后读写完成、阶段、等待对象、许可持有者与队列长度。

建立等待关系图用于诊断，识别许可/消息的循环；等待父子任务、资源和提交状态均可追踪。该图只覆盖被建模的应用等待，不宣称能识别所有原生库或驱动内部死锁。锁/许可等待、单次控制请求、进程启动与停止均有独立期限；用户等待补密码、固实大块解码与低速 HDD 不套同一个固定总时限。

    等待超期或失联 → 重新探测 / 收集脱敏快照
      → 标记未响应、停止新调度 → 协作取消
      → 必要时终止作业进程树 → 等待真实退出与句柄关闭
      → 判断最后提交点 → 可清理重试 / 保留成品 / 发布待核对

仅没有输出字节时可显示“处理中，暂无新进度”；心跳正常也不能证明解压线程无死锁。系统睡眠/恢复后重建监视基线并探测，避免把暂停期间当成普通超时。探测与停止预算是实现前可调整策略，不承诺任何固定秒数必定结束。

异步 timeout 不能强制打断不让出执行权的原生调用；已经开始的 spawn_blocking 操作也不能靠 abort 可靠停止。因此长时提取、复制和回读在隔离作业进程内执行；短时数据库/文件辅助放受限执行器，不在 UI 或异步调度线程直接执行阻塞操作。[Tokio timeout](https://docs.rs/tokio/latest/tokio/time/fn.timeout.html)、[阻塞作业](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)

Windows Job Object 约束进程树，禁止未授权脱离；退出判定使用实际进程状态，不只等某一条通知。若设备/驱动阻塞导致无法确认停止，保持“停止待确认”，保留工作区与资源归属，不开始访问同一结果的新操作、不释放占用资源、不显示已取消完成；必要时在系统重启后恢复。[Windows Job Object](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

最终发布改名仍由核心执行。若该短操作出现无响应或提交结果不明，停止后续发布，不在不确定状态尝试回滚删除；重启核实发布意图。监督机制也不能保证整个本地核心或操作系统必定可响应，因此恢复证据不能只保存在内存。

### 15.4 用户界面与诊断

界面区分等待资源、等待密码、无新进度、作业未响应、正在停止、停止待确认、发布待核对、完成但后处理待办。显示文件、阶段、最后可确认动作、影响范围与可用操作；没有循环等待证据时不直接提示“死锁”。

单项普通失败后可继续不受影响的任务；共享磁盘或状态库失败暂停依赖它的任务。采用行状态+可展开详情；共享故障使用横幅。补密码、修复分卷、调整空间、重试选中节点、核对发布、导出脱敏诊断是明确入口，不能只弹“未知错误”。停止请求走独立控制路径，数据库或数据通道失效时仍尽力发出。

诊断只记关联 ID、阶段/代次、等待关系、资源许可、队列长度、耗时、错误码和最后确认提交点；不记录候选口令。进度不逐字节刷 UI/落库；日志磁盘满、接收器停读等诊断故障不能反过来阻塞停止。

### 15.5 验收标准与交接

| 故障注入 | 验收结果 |
|---|---|
| 单 Worker、多内包；父任务等待子任务 | 外层释放执行许可；子节点能取得名额，无应用等待环 |
| 两任务反向申请源/目标盘，暂停/取消在队列中 | 整组准入，不持部分许可；取消可移除等待请求，无资源泄漏 |
| 展开中拒绝新增额度 / 缓存满 | 停到可确认边界，释放临时许可，保留文件仍计入占用；明确空间处理入口 |
| 数据库持续繁忙、旧快照升级写、不可写/损坏 | 有界等待、正确重建/拒绝操作；不无限循环、不创建空库、控制路径可执行 |
| 进度洪泛、UI 不读取、数据通道停读/断开 | 进度合并，取消和进程监视独立；结果不静默丢失，无互等退出 |
| 原生引擎停在检查点外 / 传输进程停止回应 | 探测、协作/终止和退出确认路径成立；未确认退出前不清理或重复使用目录 |
| 核心/工作进程 panic，改名成功后未提交数据库 | 未完成 Attempt 失效；成品保留并按证据补记，不重复发布或成功计数 |
| 睡眠恢复、慢固实归档、清理/日志失败 | 不误报全部成功或瞬时死锁；后处理不回滚成品，日志不堵控制通道 |

设计验收是规则与状态可追踪、重试与发布边界明确；实际验收还需静态并发检查、可控调度/压力测试、真实 Worker 与 Windows 设备故障演练。等待图无环与资源最终释放是验收依据之一，“未触发超时”或“Rust 编译通过”不是无死锁证明。

恢复代码开发后，先定义错误 DTO、控制/数据协议、许可租约与监督器，再实现故障注入；失败处置和资源释放必须先于开启多任务并行。当前仅补充设计，不代表这些机制已实现。

## 16. 用户截图补充：设置功能分类

来源：用户提供的原软件“常规”“处理”“排除”三张截图。主 agent 已逐图核对可见控件，原样保存为 reference/original-settings-general.png、original-settings-processing.png、original-settings-exclusions.png。截图中的勾选仅说明拍摄时该界面的状态，不代表用户要求新软件继承默认值，也不证明这些开关的运行效果。

Gemini 已收到主 agent 提取的可见功能清单，并只读 architecture-modern.md 给出六组分类和故障 UI 补充；本次 Gemini 没有直接接收图片。下面是复核后的设计，修正其自动排除、自动联网、无进度根因判断等建议。

| 分类 | 原图可见功能 | 我们的设置归属与推荐策略 |
|---|---|---|
| 输出管理 | 源目录/指定目录；只有一个子目录时采用该目录 | 任务配置+全局默认；输出仍为独立目录，默认保留结构。单根目录整理作为可选规则，不把普通文件散落源目录 |
| 处理策略 | 自动解内包；错误后缀修正；CRC错误仍解压；去密码首尾空格 | 内包深度/验证在任务配置摘要中可见。格式识别与源文件物理改名分开；默认不改源名、不改密码原文，CRC失败不进入正常成功发布 |
| 性能与调度 | 同时执行数；小文件优先；智能平衡CPU | 性能页；首版顺序处理，实际并发受整组物理盘/CPU/内存许可控制。默认稳定入队顺序；小包优先是可选策略，须包含等待老化避免大包饥饿 |
| 筛选与排除 | 排除特定格式（如 *.url）；排除特定文件名 | 规则编辑器分别标注“扫描输入”与“归档输出”，可预览匹配；默认没有隐藏排除规则。规则在任务开始前冻结并进入清单 |
| 完成后动作 | 删除源包；删除到回收站；整理/删除空目录Beta；提示音；完成后关机 | 首版保持源包；源删除/目录整理/关机为待评估候选，默认关闭。提示音/桌面通知为偏好项，不影响发布结果 |
| 界面与维护 | 最小化托盘；窗口置顶；自动检查更新 | 偏好页。托盘行为由用户选择，置顶默认关闭；手动更新入口，自动联网需显式启用，保持离线基线 |

原图的云密码查询、云密码获取/破解、暴力引擎与账户页属于原软件外围能力，当前产品不纳入。顶部“学习”按钮的具体规则截图无法确定；我们已有明确的成功密码自动关联，不据此增加不明操作。

筛选/排除是设计候选：扫描规则决定哪些来源进入队列；输出规则决定哪些归档条目进入最终结果。不得共用含糊的“排除”字段。建议分别支持扩展名、精确文件名及有界的 * / ? 通配匹配，明确大小写与相对路径语义，导入规则先预览；不默认配置 *.url 等规则。

应用输出过滤后，结果显示“所选内容完成（排除 N 项）”，记录排除路径/原因，不能声称原包全部内容完整交付。固实归档与引擎检验仍遵循实际能力，不承诺排除小文件必定加速。规则命中内包时必须明确是保留未展开内包还是排除该条目；目录整理不得递归改变普通文件内容。

高级候选约束：

- 去首尾空格只允许明确开启后增加派生候选，不改保险库原文。以后若纳入，成功关联必须额外记录候选变体类型及版本，实际命中的派生口令不能误当原文成功；当前 outbox 的 passwordRevision 规则仍必须满足。
- CRC异常内容若未来支持抢救，输出与正常成品区分，标损坏/部分结果，不能记录正常全部成功或触发源删除。
- 物理改名、源包删除、空目录整理与关机不因截图勾选而自动加入首版。后续若加入，规则、恢复和真实 Windows 行为单独验收；未完成、部分交付、待核对状态不触发完成后关机。
- 无进度时只说明观察事实，不擅自显示“正在深度解码”或确定为死锁；高级诊断可显示已获引擎证据，但普通界面不暴露 Job Object / Worker 等实现术语。

设置布局：左侧四个主页面保持稳定；“设置与备份”内部按六组组织，全局默认与任务覆盖分开。SSD模式、展开深度、验证范围始终有摘要，规则/危险候选用独立高级区域；普通页面按操作流程展示，设置页保留完整功能索引。

路径或输出策略改变属于配置重试：旧作业实际停止、发布状态可确认后创建新配置快照与运行代次，需要写回时创建新发布意图，不修改旧封存证据，不删除已交付成品。正常运行代次内的配置仍冻结。调整配额不等于立刻清除已有文件，占用与预留必须先核对。

本节补充参考功能和推荐策略，未将全部候选变成首版承诺，也未修改原软件配置或应用代码。
